# 第二步 · Lua 预扣与可靠投递测试结论

验收日期为 2026-11-22。开发环境使用真实 MySQL、Redis 和 RabbitMQ，独立临时活动库存为 1 份，每份含 5 次 AI 使用额度。`QuotaClaimDeliveryIT` 通过 MockMvc 调用领取接口，使用生产 Lua、投递器和入账服务。

| 验收项 | 操作与实测结果 |
| --- | --- |
| 会员校验 | 用户会员到期时间为空时领取失败。将该用户设为有效会员后，可以领取。 |
| 同用户并发去重 | 20 个工作线程对同一会员发起 100 次领取，100 次均返回同一单号及 `PROCESSING`。剩余库存为 0，Redis Stream 仅有 1 条消息。另一名有效会员收到“活动已售罄”。 |
| 暂停投递 | 关闭自动投递后，库存已扣、Stream 有 1 条待办，RabbitMQ 队列消息数为 0。活动页能按活动 ID 查到本人的原单号，另一名用户查询自己的领取结果时返回未找到。 |
| 消息不可路由 | 删除该用例的临时队列后尝试投递，投递器识别到失败。Stream 仍有 1 条消息，消费组待确认列表（PEL）有 1 条记录。 |
| 恢复补发 | 重建队列，等待 30 秒接管期后由新投递器实例补发。队列中读到原单号的持久化消息，核对了活动、用户和 5 次额度。Stream 清空，待投递索引只剩总份数标记，仍可用原单号查询处理状态。 |
| 库存恢复 | 仅删除库存键时，按预扣记录恢复出的剩余库存为 0。再删除库存、规则和 Stream 后，新领取及库存恢复均被拒绝。 |
| 最终到账 | 将已核对的原消息交回队列，启动实际消费者，活动页返回同一单号及 `GRANTED`，账户余额为 5 次，即到账 1 份。 |

这里的 30 秒是消费组允许接管未确认记录的空闲阈值。用例在同一个 JVM 内更换投递器实例，保留 Redis 数据。消费者进程强停后的 100 笔重投结果另见实施方案第 4.1 节。

在 `tripmate` 模块目录复验：

```powershell
mvn "-Dtest=QuotaClaimDeliveryIT" "-Dquota.dev.it=true" test
```
