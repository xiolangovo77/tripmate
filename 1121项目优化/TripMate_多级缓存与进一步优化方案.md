# TripMate 参考简历深度分析与进一步优化方案

> **目标：** 对照已提供的 9 份参考简历，判断 TripMate
> 是否值得引入多级缓存，并梳理除此之外值得做的工程优化。
>
> **项目定位：** AI 多人协作旅行平台，重点突出 Java
> 后端、分布式并发、缓存治理、可靠异步处理和 AI 业务落地。
>
> **核心结论：** 建议引入 Caffeine + Redis
> 多级缓存，但只用于活动配置等相对稳定的热点数据；秒杀库存、领取状态和用户额度不能简单套用普通多级缓存。相比继续增加技术名词，更重要的是形成"设计---实现---测试---指标---复盘"的完整闭环。

## 1.2 参考简历中的多级缓存做法

### 图片 5：高并发秒杀平台

其简历描述了：

-   L1 本地缓存 + L2 Redis 双层缓存。
-   布隆过滤器和空值缓存拦截非法请求。

### 图片 8：智享生活服务平台

其简历描述了：

-   Caffeine 本地缓存和 Redis 缓存组成二级缓存。
-   逻辑过期处理热点缓存击穿。
-   空值缓存处理缓存穿透。
-   数据更新后删除缓存，并通过消息补偿重试和 TTL 兜底。
-   通过压测对比多级缓存优化前后的 QPS 和平均延迟。

## 1.3 参考简历中其他值得借鉴的设计

### 缓存治理

-   缓存穿透：空值缓存；在非法 ID 查询量大且适合时考虑布隆过滤器。
-   缓存击穿：热点预热、互斥重建、逻辑过期、异步刷新。
-   缓存雪崩：TTL 随机抖动、分批预热、避免大量 Key 同时过期。
-   缓存一致性：更新数据库后删除缓存，必要时增加重试、消息补偿和 TTL
    兜底。

### 高并发链路

-   Redis Lua 原子校验和扣减库存。
-   MQ 异步处理数据库写入。
-   数据库唯一约束防止重复业务记录。
-   条件更新或乐观锁防止库存、额度变成负数。
-   死信队列、有限重试和失败补偿。
-   定时对账恢复 Redis 与数据库之间的差异。

### 流量治理

-   入口限流。
-   用户维度限流。
-   IP 维度限流。
-   令牌桶或滑动窗口。
-   消费者并发限制和消息积压治理。

### 可观测与测试

-   记录请求 ID、业务 ID、处理耗时和失败原因。
-   记录消息投递、消费和重试状态。
-   使用 JMeter 做并发压测。
-   报告 QPS、平均延迟、P95、P99、错误率。
-   使用固定测试集做回归和对照实验。

# 二、TripMate 当前缓存现状

以下内容以当前项目设计和已有简历描述为依据；新增部分属于建议方案，不能视为已经实现。

## 2.1 已有缓存

| 缓存组件 | 当前缓存内容                 | 用途                                   |
| -------- | ---------------------------- | -------------------------------------- |
| Caffeine | 各旅行对应的 AI Service 实例 | 复用实例，避免重复创建                 |
| Redis    | 各旅行的纯问答历史           | 减少重复查询 MySQL，辅助 AI 上下文组装 |

当前 Redis Key：

``` text
tripmate:chat:turns:v1:{tripId}
```

TTL：24 小时。

需要明确：

-   当前 Caffeine 缓存的是 AI Service 实例，不等同于业务数据的 L1 缓存。
-   当前 Redis 缓存的是 AI 纯问答历史，不是完整旅行数据。
-   这两种缓存各自解决不同问题，不能简单称为已经实现了 Caffeine + Redis
    二级数据缓存。

## 2.2 新增秒杀模块后可能出现的缓存

| 数据                     | 是否适合缓存     | 推荐方案                        |
| ------------------------ | ---------------- | ------------------------------- |
| 活动基本信息             | 适合             | Caffeine L1 + Redis L2          |
| 活动时间、规则、每份额度 | 适合             | Caffeine L1 + Redis L2          |
| 活动剩余库存             | 需要 Redis       | Redis 原子库存，不放 Caffeine   |
| 用户领取状态             | 需要快速查询     | Redis 快速判断 + MySQL 唯一约束 |
| 会员资格                 | 视实时性而定     | Redis；可选短 TTL Caffeine      |
| 用户可用额度             | 仅适合展示缓存   | MySQL 负责真实扣减              |
| 额度流水、领取记录       | 不做普通缓存替代 | MySQL 持久化                    |

# 三、是否应该做多级缓存

## 3.1 结论：值得做，但要限定范围

建议在 TripMate 中增加一套真正的业务数据多级缓存：

-   **L1：Caffeine 本地缓存。**
-   **L2：Redis 分布式缓存。**
-   **DB：MySQL 持久化数据源。**

推荐优先用于：

1.  秒杀活动基本信息。
2.  活动规则、活动开始和结束时间。
3.  变化不频繁的会员等级配置。
4.  其他读多写少、允许短时间最终一致的公开配置数据。

不推荐用于：

1.  秒杀剩余库存。
2.  领取资格的最终判断。
3.  用户额度的真实余额扣减。
4.  需要立即生效的权限状态。

## 3.2 推荐的多级缓存读取流程

``` mermaid
flowchart TD
    A[查询活动配置] --> B{Caffeine L1 命中?}
    B -->|是| C[直接返回]
    B -->|否| D{Redis L2 命中?}
    D -->|是| E[回填 Caffeine L1]
    E --> C
    D -->|否| F[查询 MySQL]
    F --> G{数据库是否存在?}
    G -->|存在| H[写入 Redis L2]
    H --> I[回填 Caffeine L1]
    I --> C
    G -->|不存在| J[按需缓存空值或返回不存在]
```

### 建议的初始参数

以下是开发起点，不是固定标准，后续需要压测和观察：

| 参数              | 建议初值             | 说明                   |
| ----------------- | -------------------- | ---------------------- |
| Caffeine L1 TTL   | 30～60 秒            | 本地热点配置短缓存     |
| Redis L2 TTL      | 5～10 分钟           | 分布式共享缓存         |
| TTL 随机抖动      | 基础 TTL 的 10%～20% | 避免大量 Key 同时过期  |
| Caffeine 最大容量 | 按活动数量设置       | 防止本地缓存无限增长   |
| 空值缓存 TTL      | 10～30 秒            | 只用于适合的不存在数据 |
| 逻辑过期          | 按热点程度决定       | 不要给所有 Key 都使用  |

活动配置本身变化很少，最好采用活动发布时预热、配置修改时主动失效的方式，而不是完全依赖
TTL。

## 3.3 多级缓存的一致性问题

多级缓存最大的难点不是读取，而是更新。

例如：

1.  节点 A 的 Caffeine 缓存活动库存配置。
2.  节点 B 修改了活动配置，并更新 Redis。
3.  节点 A 的 Caffeine 仍然保留旧数据。
4.  A 继续返回旧配置。

因此建议：

-   Redis 作为跨实例共享的 L2。
-   Caffeine 只缓存允许短时间陈旧的配置数据。
-   配置更新时先更新 MySQL。
-   提交成功后更新或删除 Redis。
-   通过 Redis Pub/Sub 或其他可靠失效通知机制广播本地缓存失效。
-   本地缓存设置短 TTL 作为最终兜底。
-   对关键配置可加入版本号，避免旧版本回填覆盖新版本。

如果失效通知丢失，短 TTL 和版本校验仍需保证系统最终收敛。

**不要把 Caffeine 本地缓存作为库存、领取状态和账户余额的最终数据源。**

## 3.4 活动库存为什么不能使用 Caffeine L1

库存会在活动期间高频变化。

如果每个应用实例都缓存一份库存：

-   节点 A 可能显示库存 100。
-   节点 B 已经扣减到 70。
-   节点 A 仍然返回 100。
-   如果错误地用本地缓存判断能否领取，就可能造成超卖。

正确设计：

-   Redis 保存活动库存。
-   Lua 负责库存校验和原子扣减。
-   页面查询直接读取 Redis 库存。
-   MySQL 记录最终业务结果并用于对账。
-   Caffeine 不参与库存扣减，也不参与最终资格判断。

页面库存允许是一个瞬时快照，前端展示值不能作为领取成功依据。

# 四、除了多级缓存，还有哪些优化值得做

## 4.1 缓存穿透：空值缓存与布隆过滤器

### 建议做法

对于活动详情查询：

-   活动 ID 不存在时，可以短暂缓存空值。
-   对大量随机 ID 请求，可以考虑布隆过滤器。
-   对正常活动 ID，活动创建时将 ID 加入过滤器。

### 是否值得做

**优先级：P2。**

原因：

-   活动 ID 是系统内部产生的，不一定存在大量恶意随机查询。
-   如果接口已经有登录校验和限流，穿透风险可能较低。
-   布隆过滤器有误判率，且删除和更新管理需要额外设计。

建议先做参数校验、短 TTL 空值缓存和接口限流。只有压测或日志发现大量无效
ID 请求时，再引入布隆过滤器。

## 4.2 缓存击穿：热点预热、互斥重建和逻辑过期

### 建议做法

活动发布时提前加载活动配置到 Redis 和 Caffeine。

对于确实存在热点且允许短时间陈旧的数据：

-   使用逻辑过期。
-   发现过期后只允许一个线程触发重建。
-   其他请求可以返回旧数据。
-   通过后台线程异步刷新。

### 是否值得做

**优先级：P1/P2。**

活动配置可以预热，避免活动开始瞬间缓存冷启动。

但不建议给剩余库存使用逻辑过期。库存是动态业务状态，不是允许返回旧值后参与业务决策的普通热点数据。

## 4.3 缓存雪崩：TTL 随机抖动与预热

建议：

-   不同活动配置缓存使用随机 TTL。
-   活动开始前提前预热。
-   避免所有活动 Key 在同一时间过期。
-   Redis 故障时对查询接口做限流和降级。
-   不要在 Redis 不可用时无保护地全部回源 MySQL。

**优先级：P1。**

## 4.4 数据库索引与查询优化

新增秒杀模块后，建议检查：

| 表                 | 建议索引                                                            |
| ------------------ | ------------------------------------------------------------------- |
| quota_activity     | 活动日期/业务唯一键                                                 |
| quota_claim        | `claim_id` 唯一                                                     |
| quota_claim        | `(activity_id, user_id)` 唯一                                       |
| quota_claim        | `(user_id, create_time, id)`，用于用户领取记录分页时按实际 SQL 决定 |
| user_quota_account | `user_id` 唯一                                                      |
| quota_transaction  | 业务流水号唯一                                                      |
| quota_transaction  | `(user_id, create_time, id)`，用于流水分页                          |

注意：

-   索引要根据真实查询 SQL 建立。
-   不要为了看起来复杂而建立大量冗余索引。
-   高频更新的库存字段和账户字段应考虑索引维护成本。
-   用 `EXPLAIN` 验证关键 SQL。
-   对联合索引注意最左前缀原则。

**优先级：P1。**

## 4.5 全链路限流与排队保护

参考简历中有令牌桶、滑动窗口和分用户组配额等设计。

TripMate 已经有 AOP + RRateLimiter，可以在现有基础上补充：

-   活动查询接口限流。
-   领取接口按用户限流。
-   IP 维度限流。
-   同一用户重复请求快速拒绝或返回原领取状态。
-   对活动开始瞬间设置系统级入口保护。
-   消费者并发数和 RabbitMQ Prefetch 有上限。
-   消息积压达到阈值时告警或限制新流量。

建议先沿用现有 `@RateLimit` 体系，不必再造一个完全独立的限流框架。

**优先级：P1。**

## 4.6 消息可靠性与补偿

秒杀领取链路需要覆盖：

-   消息重复投递。
-   消费者事务提交前宕机。
-   数据库提交后 ACK 前宕机。
-   RabbitMQ 暂时不可用。
-   消费失败和死信。
-   领取超时。
-   库存补偿重复执行。

建议：

-   每个领取请求使用唯一 `claimId`。
-   数据库唯一约束防止重复发放。
-   消费者先提交事务，再 ACK。
-   有限重试和死信队列。
-   补偿任务使用状态机和唯一流水。
-   对账任务定期核对 Redis 库存、领取记录和账户发放总量。

可靠消息方案应选定一种并实现完整，不要为了堆技术同时维护多套重复链路。

**优先级：P0/P1。**

## 4.7 额度账户并发安全

额度账户是新增业务中非常重要的一部分。

建议：

-   用户额度扣减使用数据库条件更新。
-   同一 AI 请求使用唯一 `requestId`。
-   额度账户更新和额度流水在同一事务中。
-   退款使用唯一退款流水号。
-   同一笔 AI 请求不能重复扣费或重复退款。
-   如果额度有有效期，使用额度批次或账户明细记录来源和过期时间。

示例 SQL：

``` sql
UPDATE user_quota_account
SET available_quota = available_quota - 1,
    total_consumed = total_consumed + 1
WHERE user_id = ?
  AND available_quota >= 1;
```

检查受影响行数，只有成功更新一行才表示扣减成功。

**优先级：P0。**

## 4.8 SSE 与状态查询优化

现有项目已有 SSE，可以用于：

-   领取状态从 accepted 到 processing。
-   领取成功或失败通知。
-   AI 行程生成状态。
-   行程修改建议状态变化。

不要每减少一份库存就向所有用户广播。

库存变化适合低频轮询或页面刷新；SSE 更适合推送当前用户自己的业务状态。

需要验证：

-   连接断开后的资源释放。
-   重连后的状态恢复。
-   用户退出旅行后的权限。
-   事件 ID 和重复事件处理。

**优先级：P1。**

## 4.9 可观测性与 Trace

参考简历中有 `ai_trace`、TraceRecord 和全链路运行追踪。

TripMate 可以补充轻量级的业务 Trace：

| 场景        | 建议记录                            |
| ----------- | ----------------------------------- |
| AI 行程生成 | requestId、耗时、Token、终态        |
| AI 修改建议 | tripId、suggestionId、状态变化      |
| 额度领取    | activityId、claimId、用户、处理耗时 |
| RabbitMQ    | messageId、消费次数、异常原因       |
| 额度消费    | requestId、扣减金额/次数、退款状态  |
| 缓存        | L1 命中、L2 命中、DB 回源、重建耗时 |

先用结构化日志和数据库审计记录即可，不必马上引入完整的
ELK、Prometheus、Grafana、Jaeger 全家桶。

**优先级：P1。**

# 五、推荐的最终缓存架构

## 5.1 数据分类

| 数据              | L1 Caffeine        | L2 Redis   | MySQL       | 最终依据                 |
| ----------------- | ------------------ | ---------- | ----------- | ------------------------ |
| 活动名称、规则    | 是                 | 是         | 是          | 活动配置                 |
| 活动开始/结束时间 | 是                 | 是         | 是          | 活动配置                 |
| 活动剩余库存      | 否                 | 是         | 对账/持久化 | Redis Lua 控制           |
| 用户领取状态      | 不建议             | 是         | 是          | MySQL 唯一约束和领取状态 |
| 会员等级配置      | 可选               | 是         | 是          | 会员业务规则             |
| 会员实时资格      | 谨慎               | 可选       | 是          | 服务端资格校验           |
| 用户可用额度      | 仅展示可选         | 仅展示可选 | 是          | MySQL 账户事务           |
| AI 纯问答历史     | 不属于活动多级缓存 | 已有       | 是          | Redis + MySQL            |
| AI Service 实例   | 已有               | 不需要     | 不需要      | Caffeine 实例复用        |

## 5.2 推荐读取流程

活动配置：

``` text
请求
  ↓
Caffeine L1
  ├── 命中 → 返回
  └── 未命中
        ↓
      Redis L2
        ├── 命中 → 回填 L1 → 返回
        └── 未命中
              ↓
            MySQL
              ↓
          写 Redis L2
              ↓
          回填 Caffeine L1
              ↓
            返回
```

活动库存：

``` text
页面查询 → Redis GET 库存 → 展示
领取请求 → Redis Lua → 校验并原子扣减
```

用户额度：

``` text
页面展示 → MySQL 查询或短 TTL 展示缓存
```

-   [ ] Redisson 锁和事务边界经过审查。
-   [ ] 事务回滚不会触发成功 SSE 通知。
-   [ ] 多人并发修改不会发生数据覆盖。
-   [ ] Redis 缓存失效和回源策略正确。
-   [ ] AI 上下文按旅行隔离。
-   [ ] SSE 断连后资源正确释放。
-   [ ] 核心业务具备自动化回归测试。

## 多级缓存

-   [ ] Caffeine L1 只缓存适合短时间陈旧的数据。
-   [ ] Redis L2 作为跨实例共享缓存。
-   [ ] 活动配置提前预热。
-   [ ] 配置更新后能够失效或刷新 L1/L2。
-   [ ] 本地缓存有 TTL 和容量上限。
-   [ ] TTL 有随机抖动。
-   [ ] 缓存穿透策略有实际场景依据。
-   [ ] 库存不进入 Caffeine L1。
-   [ ] 额度真实扣减不依赖缓存。

-   [ ] Redis Lua 原子校验和扣减库存。

-   [ ] 消费失败可以恢复或补偿。

-   [ ] AI 请求幂等扣减。

-   [ ] 库存对账和补偿任务可重复执行。

# 最终结论

**建议 TripMate 做多级缓存，但只给活动配置等稳定热点数据做 Caffeine +
Redis，不给库存、领取状态和真实额度余额盲目增加本地缓存。**

与继续堆功能相比，TripMate 当前最有价值的优化方向是：

1.  现有事务、锁、缓存和 SSE 可靠性审查。
2.  活动配置多级缓存和缓存一致性治理。
3.  Redis Lua + RabbitMQ 的会员 AI 额度秒杀。
4.  幂等、失败重试、死信和库存补偿。
5.  AI 额度消费、退款和流水闭环。
6.  限流、Trace 和 JMeter 性能验证。
7.  用真实数据优化简历表达。

**最终目标不是把 TripMate
变成技术组件展览，而是让每项技术都有业务原因、正确实现和可复现的测试证据。**
