# 接口限流

所有带 `@RateLimit` 的接口都按方法签名分别统计，用户限流再按用户 ID 隔离，IP 限流再按客户端 IP 隔离。

| 接口 | 统计对象 | 滚动窗口 | 允许请求数 |
| --- | --- | --- | --- |
| `/itinerary/add` | 每个用户 | 30 天 | 1 |
| `/itinerary/update` | 每个用户 | 30 天 | 5 |
| `/tripMessage/addAi` | 每个用户 | 30 天 | 20 |
| `/common/upload` | 每个用户 | 24 小时 | 5 |
| `/user/login` | 每个 IP | 24 小时 | 100 |
| `/user/register` | 全站共享 | 30 天 | 30 |

## 计数语义

- 30 天为 2592000 秒，不在自然月月初统一清零；已消费的额度在对应时间窗口后恢复。
- 进入业务方法前扣除一次额度，业务执行失败也计数；被限流拒绝的请求不再扣除额度。
- 用户限流要求已登录，未登录返回 `40100`，不降级为共享 IP 额度。
- 超限返回现有响应结构中的业务码 `42900` 和注解提示。HTTP 状态沿用项目现有约定，前端按业务码处理。
- 限流器的空闲过期时间取配置 TTL 与统计窗口的较大值，避免提前过期恢复额度。
- IP 读取沿用 `X-Forwarded-For`、`X-Real-IP`、远端地址的顺序。部署时须由可信代理覆盖转发头并限制后端直连，否则客户端伪造转发头可绕过 IP 限流。

## 修复与部署

旧实现的用户 key 只有用户 ID，导致行程添加、更新、AI 和头像上传共用额度；`trySetRate` 仅初始化一次，使最先创建的配置覆盖其他接口的实际行为。

旧限流缓存已手动清理，现在使用稳定的 `rate_limit:<接口签名>:user:<用户ID>` 等 key；配置了附加前缀时，前缀放在接口签名前。不再附加版本号、次数、窗口和 TTL。不同接口互不影响，同一接口、同一用户的后续请求复用原额度。

清理缓存后，下一次请求通过 `trySetRate` 初始化注解中的规则。后续请求不会重置计数；不要在每次请求时调用 `setRate`，这会恢复已消费的额度。以后如果修改次数、窗口或 TTL，需要在部署时删除对应的限流器（通过 `RRateLimiter.delete()` 一并删除配置及其计数子 key），或等其空闲过期，单纯重启不会覆盖 Redis 中的旧规则。多实例部署应统一规则并完成所有实例更新后再清理相关限流器，避免旧实例重新初始化旧规则。

## 验证

在 `tripmate` 目录运行：

```shell
mvn -o -Dtest=RateLimitAspectTest test
```

测试通过真实控制器的 Spring AOP 代理及 MockMvc 检查额度边界、接口与用户隔离、登录/注册规则、计数复用与清理后初始化、TTL 下限、并发拒绝和业务错误响应。Redis 使用按 key 共享的原子额度模拟，未连接真实 Redis 或调用外部 AI。
